## Dataset reproducibility problems

- `dataset/text_numeric_generator_for_llm.py` has no explicit random seed.
- It uses both Python `random` and NumPy RNGs without coordinated seeding.
- It executes large dataset-generation calls at module import time.
- Output paths are relative to the current working directory rather than an explicit dataset destination.
- There are no train/validation/test split manifests.
- There are no dataset hashes, generator-version metadata, or schema/version identifiers.
- Large generated files are tracked directly in Git, adding roughly 105 MB of working-tree data.

## Runtime and dependency blockers

The existing `requirements.txt` is a captured environment rather than a minimal project dependency specification.

Key problems:

- It pins `torch==1.13.1`, which is not a viable baseline for the workstation's default Python 3.14.
- It mixes CUDA 11 and CUDA 12 runtime packages.
- It includes many unrelated notebook, web, vision, audio, and UI packages.
- It contains a trailing package entry named `data`.
- It pins older `transformers==4.29.2` and related packages without documenting why.
- A clean install has not been demonstrated.

Current runtime validation is therefore blocked before model execution begins.

## Core wrapper findings

#

## Numeric-to-numeric path

The path is structurally coherent but inefficient and underspecified.
A scalar is projected to hidden size and then repeated across the model's full `n_positions` sequence length.
For GPT-2 this means processing approximately 1,024 repeated tokens for one scalar input.
That creates unnecessary compute/memory cost and makes the intended representation mechanism unclear.

The future implementation should define whether one projected numeric value is one sequence token, or whether repetition is an explicit ablation rather than an accidental default.

### Text-to-numeric path

The current path tokenizes text normally and projects the final transformer hidden state to a scalar.
The transformer is frozen and only the output projection is trained.

Correctness risk: the code uses `last_hidden_state[:, -1, :]`.
For padded batches, the final tensor position can be padding rather than the last valid token.
The output representation should be selected from the last valid token using `attention_mask`, or use another explicitly defined pooling rule.

The Stage-1-to-Stage-2 checkpoint transfer also needs to be evaluated rather than assumed useful.
Stage 1 learns output mapping from hidden states produced by projected numeric embeddings; Stage 2 receives ordinary token embeddings.
The initialization may transfer or may not.

#

## Checkpoint design

All training scripts save `llm.state_dict()`, which includes the entire frozen base language model.
For GPT-2 and especially GPT-2 Large this makes checkpoints unnecessarily large.
The loader also accepts all keys containing `model`, so frozen base-model weights are copied back from checkpoints.

The finished project should default to projection-only checkpoints plus metadata and support legacy full-state checkpoints only for compatibility.

## Mixed-input path — blocking defects

The mixed path should be treated as non-functional until CP8.

Observed defects:

1. Text embeddings and numeric embeddings are concatenated along hidden dimension, producing approximately `2 * hidden_size`; GPT-2 expects exactly `hidden_size`.
2. `_process_mixed_input` joins an entire batch of processed strings into one string, collapsing batch structure.
3. Parsed numeric values returned by `_process_mixed_input` are then replaced by `inputs["numeric_inputs"]`, so part of the parsing result is unused.
4. Current generated mixed training text is only a numeric marker; after marker removal, the text content becomes empty.
5. `numeric_inputs.squeeze()` in `alignmentMixedN.py` can become a scalar for batch size 1 and therefore fail iteration.
6. The input projection is configured as non-trainable in mixed training even though projected numeric embeddings are central to the method.
7. There is no mapping from each numeric placeholder to a specific sequence position.
8. Multiple numeric placeholders per sample are not represented correctly.

This is an architectural defect, not a small bug fix.

## Training/evaluation audit

Current scripts report training MSE only.
There is no independent validation or test set, no deterministic seed, no structured metrics file, and no experiment manifest.
There is also no baseline comparison, no out-of-range evaluation, and no statistical replication across seeds.Additional training issues:

- Config parsing, CLI definitions, device resolution, and path helpers are duplicated across three scripts.
- Scheduler behavior is not documented consistently. The code uses `StepLR(..., gamma=0.1)`, while the README describes reduction by a factor of 2.
- AMP uses the older `torch.cuda.amp` interface and should be normalized when dependencies are modernized.
- No run records include Git SHA, model revision, package versions, seed, device, timing, or VRAM.
- No test verifies that frozen transformer parameters remain unchanged after training.

## Benchmark audit

`Benchmarks_training/Aignment_numeric2numeric_GPT2-large.xlsx` contains one sheet with 11 populated rows and 13 columns.
It records a few batch-size, elapsed-time, CUDA-memory, learning-rate, and epoch/loss observations.
`Benchmarks_training/Book3.xlsx` contains a smaller duplicate-like batch-size table.

These are useful historical notes, but they are not reproducible benchmark artifacts because they lack:

- exact commit and code version,
- model repository revision,
- dataset or generator seed,
- metric definitions,
- complete training configuration,
- hardware/software environment,
- command line,
- checkpoint identity,
- repeated-run statistics.

Historical benchmark claims should be retained as legacy observations and replaced by structured reproducible results in CP10.

## Documentation accuracy findings

The current README predates the stabilized code and contains statements that should not be treated as current validation.

Examples:

- It describes customized tokenizers, but the code currently uses `AutoTokenizer` directly.
- It refers to "diffusion layers", but the implemented wrapper contains linear projection layers and a pretrained transformer.
- It reports historical 2% and 25% error figures without defining the error metric or linking to reproducible run artifacts.
- It says checkpoints are stored in CHK, while no tracked checkpoints are present.
- It describes a factor-of-two scheduler reduction while the code currently uses `gamma=0.1`.

These claims should be separated into a clearly labeled historical-results section until CP10 reproduces or supersedes them.

## Repository engineering gaps

The repository currently has no:

- installable package structure or `pyproject.toml`,
- shared configuration/schema module,
- formal checkpoint schema,
- pytest test suite,
- CI workflow,
- deterministic data manifest,
- unified train/evaluate command,
- structured result format,
- release checklist or versioning policy.

There is also no explicit license in the current tree, which should be resolved before a public release.

## Risk ranking

## Critical
- Runtime environment is not yet installable/reproduced.
- Mixed-input architecture is invalid in its current form.

## High
- Full frozen base model is saved in every checkpoint.
- Numeric input path processes a full repeated sequence for one scalar.
- Text output pooling can select padded positions.
- Dataset generation has import-time side effects and no seed.
- There is no validation/test evaluation or experiment provenance.
- Historical performance claims are not reproducible.

#

## Medium
- Large generated datasets are tracked in Git.
- Training utilities and CLI logic are duplicated.
- README terminology and scheduler description are stale.
- Packaging, linting, CI, and release metadata are absent.

## Audit conclusion

CP1 should be considered a syntax/configuration stabilization checkpoint, not a validated training release.
The data files themselves are internally consistent, the workstation hardware is sufficient, and the project is recoverable without changing its core research hypothesis.
The shortest reliable path to completion is CP2 through CP11 as specified in `docs/ROADMAP_CP2_CP11.md`.
